# HR Agent 能力与性能测试报告

测试日期：2026-09-10  
测试对象：hr-agent-study  
报告类型：组件级实测 + 静态容量核查 + 历史真实链路抽样  
结论级别：可复现技术验证，不等同于生产容量认证

## 1. 执行摘要

| 指标 | 本次结果 | 口径 |
|---|---:|---|
| JD 生成支持量 | 无本地固定总量上限 | 代码未限制总 JD 数；列表接口单页最大 100 条，前端页容量最大 50 |
| JD 并发验证 | 5 路并发，成功率 100% | 直接调用 LLM 生成，不含 Dify、鉴权、保存和前端展示 |
| JD 生成时延 | p50 20.444s，p95 25.204s | 10 次直接 LLM 调用的组件时延 |
| 简历评估覆盖量 | 6 份合成简历 | 模型级模拟评分，不含 Dify 工作流、文件解析和数据库写入 |
| 简历评估排序准确率 | 100% | 强匹配与弱匹配的 9 组两两比较，样本仅 6 份，不能外推为生产准确率 |
| 知识库测试规模 | 100 份 FAQ + 20 条查询 | 合成语料，直接调用 Embedding API |
| 检索 Top-k | 实际上下文 Top-k = 5 | `CONTEXT_LIMIT=5`；候选排序上限 `RERANK_TOP_K=10` |
| 向量检索准确率 | Recall@1 100%，Recall@5 100%，MRR 1.000 | 100 份合成 FAQ，查询与文档区分度较高 |
| Rerank 实测 | 未完成 | Qwen rerank 返回 403：免费额度已耗尽 |
| RAG 组件串联时延 | p50 4.105s，p95 4.918s | 3 条查询；Embedding + 内存检索 + LLM 回答，不含 pgvector、HTTP、Rerank、流式开销 |
| 远程服务读取时延 | p50 1.330s，p95 1.448s | 10 次 JD 列表读取，单页 100 条 |
| 历史真实 JD 链路 | 约 8s | 单个成功样本：Dify 流式生成开始到进入保存 |
| 历史真实评分标准链路 | 约 19s | 单个成功样本：Dify 流式生成开始到进入保存 |

核心结论：

1. 当前代码对“JD 总数”“简历批量总数”“知识库文档总数”都没有应用层硬上限，实际容量取决于 Dify、PostgreSQL/pgvector、远端 HR 服务和模型配额。
2. 本次可以验证模型、Embedding、远程服务读取和组件串联性能，但不能验证完整 Dify 工作流、真实文件解析、pgvector 检索和端到端 HTTP 链路，因为测试时本机 Dify 与 PostgreSQL 均未启动。
3. 100% 检索准确率和简历排序准确率来自小规模合成数据，只证明链路可用，不能直接作为生产 SLA。

### 5.3 Rerank 测试

执行时使用 `gte-rerank-v2` 对每个查询的 Top-10 候选尝试重排，接口返回：

```text
403: Free quota exhausted.
```

因此本次没有可用的 Rerank 准确率和时延结果，不能将向量检索指标等同于“融合检索 + Rerank”准确率。

## 6. Top-k 与检索链路

| 环节 | 数量 |
|---|---:|
| 向量检索请求 | Top-5 |
| 全文检索请求 | Top-5 |
| 合并后最低相似度 | 0.2 |
| 重排候选上限 | 10 |
| Rerank 配置最终值 | 10 |
| RAG 实际传入的最终 Top-k | 5 |

结论：当前用户问题的最终上下文规模是 **5 个 chunk**。虽然 `RERANK_FINAL_K=10`，但 `ask_question_stream` 把 `context_limit=5` 作为最终 `top_k` 传给重排服务，因此实际最终结果仍为 5。

建议生产配置明确统一为：

```text
CONTEXT_LIMIT=5
RERANK_TOP_K=10
RERANK_FINAL_K=5
```

或者修改 RAG 调用，让最终 Top-k 独立使用 `RERANK_FINAL_K`。目前配置值 10 容易造成误解。

## 9. 建议验收方案

建议下一轮在 Dify、PostgreSQL/pgvector 均启动后执行：

| 场景 | 样本量 | 通过标准建议 |
|---|---:|---|
| JD 生成 | 50 个岗位 | 结构合格率 >= 95%，E2E p95 <= 30s |
| 简历评估 | 50 份真实脱敏简历 | 评分排序一致率 >= 85%，p95 <= 15s |
| 知识库检索 | 100 / 1000 / 5000 份文档 | Recall@5 >= 90%，Rerank 后 nDCG@5 提升 >= 5% |
| RAG 问答 | 100 条标注问题 | 答案正确率 >= 85%，引用正确率 >= 90% |
| 并发能力 | 1 / 5 / 10 / 20 用户 | 无 5xx，p95 不超过单用户基线的 3 倍 |
| 文件解析 | PDF/DOC/DOCX/TXT 各 20 份 | 成功率 >= 98%，无乱码和空文本 |

## 10. 最终结论

本次测试证明了以下部分可用：

1. 远程 HR 服务读取稳定，10/10 成功，p95 1.448s。
2. LLM 可直接生成结构完整的 JD，5 路并发成功率 100%，但单次生成较慢。
3. Embedding 对 100 份 FAQ 的 Top-5 基本召回能力正确。
4. 6 份合成简历的模型级强弱排序全部正确。

本次测试不能证明以下生产指标：

1. Dify JD、简历评分、RAG 问答的真正 E2E 准确率和时延。
2. pgvector 在 1000 份以上文档和多用户并发下的召回与性能。
3. Rerank 的收益、Top-k 最优值和额度可用性。
4. 文件解析在真实简历和知识库文档上的成功率。

因此，本报告可作为当前版本的技术基线，但不应作为生产容量承诺或最终验收报告。
